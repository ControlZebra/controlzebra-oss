# Logix VCS Custom Tools Sidecar Integration Plan (Wails v3, Windows)

**Author:** GitHub Copilot (GPT-5.3-Codex)  
**Date:** 2026-02-21  
**Status:** Planning (Updated Scope)

---

## 1) Confirmed Scope (Locked)

- **Install model:** Support both, with bundled sidecar as primary and user-installed fallback.
- **Communication model:** **CLI invocation per operation** (no long-running daemon).
- **Supported commands only:** `explode`, `implode`, `acd2l5x`, `l5x2acd`.
- **Auto behavior:** `acd2l5x` runs automatically when a tracked `.acd` file changes.
- **Auto output location:** store auto-generated L5X files under `.controlzebra/preview/acd` (Windows: `.controlzebra\preview\acd`).
- **UI behavior:** For `.l5x` file context menu show `Export > Explode`, `Export > Implode`, `Export > L5X to ACD`.
- **Explode output location:** create a new directory in the same parent folder as the source `.l5x` file.
- **Out of scope:** All other `l5xgit`/`l5xplode` commands are explicitly unsupported in ControlZebra.

---

## 2) Goal

Integrate Rockwell `ra-logix-designer-vcs-custom-tools` into ControlZebra as a Windows-focused sidecar capability that only handles conversion/export workflows for `.acd` and `.l5x` files.

---

## 3) Command Contract (Strict Allowlist)

ControlZebra backend exposes only these operations:

1. `AcdToL5x(acdPath)` → wraps `acd2l5x`
2. `L5xToAcd(l5xPath, acdPath)` → wraps `l5x2acd`
3. `Explode(l5xPath, outputDir)` → wraps `explode`
4. `Implode(inputDir, l5xPath)` → wraps `implode`

Rules:

- No generic `RunCommand(command, args...)` public API.
- No passthrough args from frontend.
- Input validation is strict (`.acd`, `.l5x`, dir existence, repo ownership checks where applicable).
- `AcdToL5x` auto-trigger writes output to `.controlzebra/preview/acd` using deterministic naming per source `.acd`.
- `Explode` always creates its output directory next to the source `.l5x` file (sibling directory), not in `.controlzebra`.
- Commands outside this set return a typed “unsupported operation” error.

---

## 4) Integration Architecture

Reuse existing patterns:

- `services/updater_service.go` for sidecar process lifecycle pattern
- `services/local_bin_service.go` for bundled/fallback binary resolution
- `services/runner.go` for timeout and process execution

Add dedicated `LogixVCSService` in backend:

- `GetStatus()` (tool availability and resolved paths)
- `ValidateEnvironment()` (Windows + Studio/SDK prerequisite checks)
- explicit operation methods only: `AcdToL5x`, `L5xToAcd`, `Explode`, `Implode`

---

## 5) UX + Trigger Requirements

## 5.1 Automatic `.acd` change trigger

When a `.acd` file changes:

1. Detect change via existing repository/file-watch flow.
2. Debounce and coalesce rapid writes.
3. Run `acd2l5x` automatically in background.
4. Write generated `.l5x` into `.controlzebra/preview/acd`.
4. Capture and surface result in existing operation/log mechanism.

Guardrails:

- Do not retrigger from files generated by the conversion itself.
- Skip auto-run when prerequisites are missing and emit a clear status error.
- Ensure one conversion per file at a time (per-file lock).
- Ensure `.controlzebra/preview/acd` exists (create if missing).

## 5.2 `.l5x` context menu export actions

For `.l5x` file context menu, add:

- `Export > Explode`
- `Export > Implode`
- `Export > L5X to ACD`

Behavior:

- Menu entries appear only for `.l5x` selection.
- Actions call dedicated backend methods (no command string passing).
- `Explode` creates a new sibling directory in the same parent folder as the selected `.l5x`.
- Errors are mapped to actionable user messages.

## 6) Phased Implementation

## Phase 0 — Packaging + Availability

1. Finalize binary sourcing/signing for `l5xgit.exe` / `l5xplode.exe`.
2. Implement resolver order: bundled → managed local path → PATH.
3. Add status diagnostics for which source is active.

## Phase 1 — Backend Core

1. Add `services/logix_vcs_service.go`.
2. Implement strict 4-command wrappers and validation.
3. Register service in `main.go` and generate bindings.
4. Add tests for allowlist, validation, and resolver behavior.

## Phase 2 — Auto Trigger Wiring

1. Integrate `.acd` change detector hook.
2. Add debounce + per-file lock to prevent duplicate runs.
3. Add operation event emission and error mapping.

## Phase 3 — Context Menu Wiring

1. Add `.l5x` context menu export submenu in frontend.
2. Wire each action to backend method.
3. Add disabled-state handling when tool/prereqs unavailable.

## Phase 4 — Validation + Rollout

1. Windows QA for all 4 operations.
2. Confirm no unsupported commands are callable.
3. Regression test existing git workflows remain unchanged.

## 8) Risks and Mitigations

1. **Studio 5000 SDK dependency for conversions**
   - Mitigation: preflight checks + explicit “missing prerequisite” errors.
2. **Long conversion runtime**
   - Mitigation: command-specific timeouts, cancellation support, and serialized per-file execution.
3. **Auto-trigger loops/noise**
   - Mitigation: debounce, origin tagging, and conversion output ignore rules.
4. **Scope creep into other commands**
   - Mitigation: strict non-extensible allowlist and tests that reject unsupported commands.

---

## 9) Exit Criteria

Complete when all are true:

- Only 4 supported operations are exposed through backend bindings.
- `.acd` file change automatically triggers `acd2l5x`, writes to `.controlzebra/preview/acd`, and logs outcome.
- `.l5x` context menu shows `Export` submenu with exactly 3 actions (`Explode`, `Implode`, `L5X to ACD`).
- `Explode` output directory is created as a sibling of the source `.l5x` file.
- Unsupported commands are blocked by design and verified in tests.
- Existing non-Logix workflows continue to behave as before.

---

## 10) Explicitly Unsupported in ControlZebra

- `commit`
- `difftool`
- `restoreacd`
- any other `l5xgit` or `l5xplode` command not listed in section 3

This list is intentional and should remain enforced unless product scope changes.
